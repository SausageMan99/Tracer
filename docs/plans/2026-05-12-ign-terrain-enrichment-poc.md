# IGN Terrain Enrichment POC Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Prove whether IGN/open French terrain data can improve TrailForge route decisions on Tourville, Caen, and Meudon without replacing OSM or weakening surface honesty.

**Architecture:** Keep OSM as the routing graph. Add an offline-first IGN terrain enrichment layer that annotates existing OSM edges with contextual signals: landcover, forest/park proximity, hydro proximity, slope/elevation confidence, artificialization, and optional IGN path proximity. The POC must first write diagnostic artifacts, then only later feed scoring if evidence is positive.

**Tech Stack:** TypeScript/Node.js existing TrailForge engine, GeoJSON fixtures for POC, optional Python/geopandas only for data preprocessing if needed, existing benchmark artifacts under `artifacts/route-benchmark-results/`, Vitest for contract tests.

---

## Product decision

Do not integrate IGN as a replacement routing provider. The POC is an enrichment layer for confidence and scoring.

OSM remains responsible for:
- routable graph;
- `highway`, `surface`, `tracktype`, `access`, relations;
- geometry used by solver.

IGN/open data is responsible for:
- terrain context around each edge;
- forest/park/natural/water/artificialized signals;
- elevation/slope confidence;
- path-confidence cross-checks where usable;
- better diagnosis of “OSM has paths but labels are incomplete”.

Hard rule: IGN context can raise `naturalContext` or `scenicContext`, but must not convert explicit OSM `asphalt`, `concrete`, or `paved` into trail/non-paved.

---

## POC scope

### Zones

Use only three blocker zones first:

1. Tourville-sur-Odon / Bois des Amis de Jean Bosco / Château de Baron
2. Caen Colline aux Oiseaux
3. Meudon forest / restricted-access ambiguity

### Success criteria

The POC is useful if it can answer these questions with artifacts:

- Tourville: can IGN identify real wooded corridors and distinguish “road transition to woods” from “contour parasite around woods”?
- Caen: can IGN confirm this is a compact park/recovery context, where clean adjusted distance is better than dirty exact 6 km?
- Meudon: can IGN help distinguish “forest exists nearby” from “accessible coherent trail graph exists from this start”?
- Surface honesty: do explicit paved/asphalt/concrete edges remain paved while still receiving a separate natural/scenic context if applicable?

The POC fails if it only adds vague scenic boosting without changing diagnostic clarity.

---

## Data sources to evaluate

### Required for POC

- OSM current graph/artifacts already generated by TrailForge.
- IGN/open landcover/occupation data: OCS GE or equivalent open French landcover layer where available.
- IGN/open elevation: RGE ALTI or preprocessed elevation source if practical.
- Forest/natural/hydro layers from IGN/data.gouv/open public sources where licensing permits reuse.

### Optional after POC

- BD TOPO path/road features as a cross-check against OSM.
- Plan IGN/SCAN 25 only for human validation screenshots, not automated ingestion unless license/API use is clear.

### Prohibited without explicit rights

- Scraping Strava Heatmap, Komoot, AllTrails, Wikiloc, OpenRunner.
- Using proprietary GPX/routes from third-party platforms.
- Screenshot/tile extraction as training data.

## Data model

Create a first-class type for enrichment, separate from existing OSM fields.

```ts
export interface TerrainContextSignals {
  source: 'ign_poc_fixture' | 'ign_cache' | 'none';
  landcoverClass?: 'forest' | 'park' | 'grassland' | 'water_corridor' | 'urban' | 'agriculture' | 'unknown';
  naturalContextScore: number; // 0..1
  artificializationScore: number; // 0..1
  forestProximityM?: number;
  parkProximityM?: number;
  waterProximityM?: number;
  slopeMeanPct?: number;
  slopeMaxPct?: number;
  ignPathProximityM?: number;
  confidence: 'low' | 'medium' | 'high';
  warnings: string[];
}
```

Add it to `EnrichedEdge` only after tests prove compatibility, likely in `lib/types.ts`:

```ts
terrainContext?: TerrainContextSignals;
```

Interpretation rule:

```ts
const explicitPaved = ['asphalt', 'concrete', 'paved', 'sett', 'paving_stones'].includes(edge.surface ?? '');
const naturalContext = edge.terrainContext?.naturalContextScore ?? 0;
// naturalContext may affect scenic/natural-context metrics, not pavedRatio/trailRatio.
```

## Risks

### Risk 1: GeoData complexity eats the product work

Mitigation: fixture-first. No PostGIS, no France-wide ingestion, no live API calls in the first POC.

### Risk 2: IGN context creates fake trail confidence

Mitigation: separate surface ratios from terrain context ratios. Paved remains paved.

### Risk 3: Licensing ambiguity

Mitigation: store source/license metadata in every fixture/artifact. Do not ingest proprietary platforms.

### Risk 4: Slow live route generation

Mitigation: offline/precomputed cache. No live WFS calls per generation.

---

## Final acceptance criteria

The POC is accepted if:

- `npm run ign:poc` generates artifacts for Tourville, Caen, and Meudon.
- Tests prove asphalt/concrete/paved are never reclassified as trail/non-paved.
- Artifacts show useful new context fields per edge.
- A human-readable summary gives a GO/NO-GO on scoring integration.
- Existing technical gates remain green.

The POC is rejected if:

- It cannot explain any current blocker better than existing OSM diagnostics.
- It requires live network calls during route generation.
- It risks hiding bad paved routes behind natural/scenic context.
- It adds heavy geodata infrastructure before proving product value.
